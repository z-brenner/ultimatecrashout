# Add a fighter pack

An open fighter lives entirely in `fighters/<id>/`. Once the pack is complete
and marked `ready`, the game registry, the 2D/3D lists, the effects, and the
rendering manifests are generated automatically. Adding a character therefore
requires no manual changes under `src/`.

## Quick start (2D sprite strips — the fastest path)

```sh
npm run fighter:new -- my-fighter --kind 2d
```

This creates a draft:

```text
fighters/my-fighter/
├── fighter.json  # identity, gameplay, moves, license, and effects
├── render.json   # sprite-strip settings
└── sprites/      # one PNG strip per animation slot
```

1. Draw horizontal PNG strips and save them as `sprites/<slot>.png`
   (`idle.png`, `walk.png`, `jab.png`, …). Every frame in a strip has the size
   set by `spriteStrips.frameWidth`/`frameHeight`, a transparent background,
   the character facing `visual.sourceFacing`, and feet on the bottom edge.
   Only `idle.png` is required: a missing slot borrows a related strip (for
   example `fast_fall` uses `fall`, `forward_smash` uses `forward_tilt`) and is
   reported as `author_required` until you draw it. The 50 slot names are the
   keys of `threeD.slotProfiles.platform-fighter` in `pipeline.config.json`.
2. Fill in `fighter.json`: name, colors, movement, specials, and optionally
   your own moves and hitboxes (see "Authoring moves" below). Set
   `spriteReferenceHeight` to the idle sprite's opaque height in pixels.
3. Set `status` to `ready`, then build and validate:

```sh
npm run fighter:build -- my-fighter   # needs ffmpeg, ffprobe and cwebp
npm run fighter:check
npm run dev                            # the fighter is now on the select screen
```

`npm run content:doctor` reports any missing tool. No step needs Blender,
zsh, or the private `assets-source/` vault. [`buckle`](buckle/) is a complete
reference pack built this way; its strips are generated by
`scripts/starter_fighter/generate_sprites.py`.

### Other source formats

`render.json` may instead declare explicit `actions` (`sequence`, `files`,
`strip`, `grid-sheet`, `json-sheet`, or `unity-sheet`) and classify every slot
under `slots.direct`, `slots.adapted`, and `slots.author_required`; the
existing 2D packs show each format. 3D packs (`--kind 3d`) are rendered to the
same atlases offline with Blender; see `scripts/open_fighter_pipeline/`.

## Pack contract

`fighter.json` follows [fighter.schema.json](fighter.schema.json). Its main
fields are:

- `id`: identical to the folder name, using lowercase letters and hyphens;
- `order`: a unique position among `ready` packs;
- `identity`: display name, archetype, play style, and colors;
- `gameplay`: hurtbox, weight, movement, and four special moves;
- `visual`: orientation, attribution, source page, and license;
- `effects`: material for each attack and shared visual traits;
- `audio` (optional): the fighter's own sounds (see "Sounds and voice").

`render.json` maps upstream files to the engine's 50 animation roles. For 2D,
every slot must be classified exactly once as `direct`, `adapted`, or
`author_required`. For 3D, the model, rig, slot profile, and action aliases are
required.

If the model, animations, or other elements come from separate packs, declare
each additional source in `render.json` with `additionalSources` (`role`,
`name`, `author`, `sourcePage`, `license`, and `licenseUrl`). This information
is copied into the public provenance record.

These grades are not equivalent:

- `direct`: a source animation genuinely designed for this movement;
- `adapted`: a real, usable source clip that is not dedicated to the movement;
- `author_required`: a temporary fallback; a dedicated animation still needs
  to be created.

A pack can be playable without being ready for publication. The validation
command reports this distinction and never presents a fallback clip as a real
attack animation.

## Assets and licensing

Local sources referenced by `render.json` must exist under
`assets-source/open-fighters/`, together with their provenance and SHA-256
checksums. The source page and license must match in `fighter.json` and
`render.json`. Do not use an asset unless its redistribution and modification
rights are explicit.

The `sourceProvenance` and `sourceSha256Manifest` fields in 2D packs are audit
pointers to this local source vault; they are intentionally not resolved in a
public clone. The URLs, licenses, transformations, and checksums for distributed
derivatives remain in the pack and under `public/assets/characters/open/`.

For each `00` variant, the renderer produces:

- 50 WebP atlases under `public/assets/characters/open/<id>/00/`;
- `PROVENANCE.json` and `SHA256SUMS`;
- a portrait under `public/assets/ui/fighters/<id>/select/00.png` and its
  `00.thumb.webp` WebP thumbnail for the character-select screen;
- the 2D or 3D animation metadata expected by the runtime.

## What is automated

`npm run fighter:build` validates the `ready` packs, sorts them by order, and
regenerates:

- `src/game/generated/openFighterRegistry.ts`;
- `scripts/open_fighter_pipeline/manifest.json`;
- `scripts/open_fighter_pipeline/2d_manifest.json`.

Do not edit these three outputs manually. They are also synchronized by
`npm run dev`, `npm test`, and `npm run build`.

While `npm run dev` is running, gameplay data needs no manual rebuild: saving
`fighter.json` (or anything else in the pack) re-validates and re-syncs the
registry and reloads the page. Art changes in a 2D `render.json` or in
`sprites/` take effect when `npm run fighter:build -- <id>` rebuilds the
atlases; run it in another terminal and the dev server waits for the whole
build (atlases, thumbnails, checksums), then reloads once, with no server
restart. An invalid pack shows the validator's
message, with the exact field, in the browser's error overlay until it is
fixed.

The targeted `npm run fighter:build -- <id>` command automatically regenerates
the fighter thumbnail. After manually replacing multiple fighter portraits or
stage previews, run `npm run optimize:ui-assets`.

Stats, movement tuning, animation mapping, all four special moves, and effects
already supported by the engine are configurable in the pack. A completely new
mechanic, such as a new kind of tether, a transformation, or unsupported
projectile behavior, still requires an engine implementation before the pack
can reference it.

## Authoring moves, hitboxes, and knockback

Without extra data, every fighter receives the engine's generated kit: 13
standard attacks scaled by the optional `gameplay.power`, `gameplay.speed`,
and `gameplay.reach` multipliers (`power` scales damage only; as in Smash, a
hard hitter KOs earlier because its damage feeds the knockback formula), plus the four specials declared under
`gameplay.specials`. To give a fighter its own moves, add `gameplay.attacks`.
Each key is one of the 17 move names, and each value replaces only the fields
it declares:

```json
"gameplay": {
  "maxJumps": 3,
  "attacks": {
    "jab": { "label": "Snap Jab", "damage": 4, "startup": 2, "active": 3, "recovery": 8 },
    "forward-smash": {
      "damage": 19,
      "angle": 38,
      "baseKnockback": 30,
      "knockbackGrowth": 0.76,
      "hitboxes": [
        { "offset": { "x": 24, "y": 10 }, "radius": 16, "kind": "sour", "priority": 2 },
        { "offset": { "x": 48, "y": 10 }, "endOffset": { "x": 60, "y": 4 }, "radius": 14,
          "activeStart": 0, "activeEnd": 3, "kind": "sweet", "damageMultiplier": 1.15 }
      ]
    }
  },
  "throws": { "back": { "damage": 11, "baseKnockback": 60 } }
}
```

Rules worth knowing:

- Authored values are absolute; `power`, `speed`, and `reach` do not rescale
  them. Frame counts run at 60 frames per second.
- `angle` is in degrees: `0` launches forward, `90` straight up, `270` straight
  down. It is mirrored automatically when the fighter faces left.
- Hitbox `offset` is in fighter-local world units: `x` points forward, `y`
  points up from the fighter's center. `activeStart`/`activeEnd` count from the
  first active frame; a hitbox with `endOffset` sweeps linearly between the two
  positions. When several bubbles touch a target, the highest `priority` wins.
- Without `hitboxes`, the engine derives a compact sweet/sour chain from
  `offset` and `radius`.
- When you change `damage` without authoring `hitstop` or `shieldDamage`,
  those two are recomputed from the new damage.
- `throws`, `maxJumps` (1–6), `shieldHealth`, `shieldRegen`, `traction`, and
  `airAcceleration` are optional fighter-wide overrides.
- Specials may also be overridden here, for example to author knockback that
  `gameplay.specials` would otherwise derive from damage.
- Keep KO percents Smash-like. On Verdant Grove against a mid-weight at
  centre stage, uncharged, the generated kit KOs with forward smash around
  108%, up and down smash around 125%, forward air around 135%, forward tilt
  around 165% and up air around 180%; a full charge adds 40% damage (not
  knockback) and takes a forward smash to about 66%. `src/game/koMeasure.ts`
  measures any move through the engine's hit path
  (`koPercent(attacker, target, move)`), and
  `koCalibration.test.ts` fails a pack whose move KOs a mid-weight under 70%.

### Move timing, armor, and per-hitbox launches

Every frame number below counts from the move's first frame (`0`), and every
window is inclusive.

| Field | Applies to | Effect |
| --- | --- | --- |
| `landingLag` | aerials | Frames of lag when the aerial lands. An L-cancel halves it. Defaults to `recovery × 0.42`, clamped to 6–16. |
| `autoCancel: { "before": 3, "after": 30 }` | aerials | Landing before frame `before`, or on/after frame `after`, uses the 4-frame auto-cancel landing instead. Either bound may be omitted. |
| `intangible: { "start": 0, "end": 5 }` | any move | Nothing can hit or grab the fighter during those frames. |
| `superArmor: { "start": 4, "end": 14 }` | any move | Hits still deal damage and hitstop but do not flinch, launch, or interrupt the move. |
| hitbox `angle`, `baseKnockback`, `knockbackGrowth` | any hitbox | Override the move's launch for hits from that bubble, e.g. a spiking sweet spot and an outward sour spot. |

```json
"down-air": {
  "landingLag": 20,
  "autoCancel": { "before": 3, "after": 32 },
  "hitboxes": [
    { "offset": { "x": 4, "y": -48 }, "radius": 14, "kind": "sweet", "activeStart": 0, "activeEnd": 2 },
    { "offset": { "x": 0, "y": -30 }, "radius": 13, "kind": "sour", "angle": 45 }
  ]
}
```

Notes:

- A chargeable smash holds its frame while charging, and windows do not apply
  during the hold. Count windows on the move as if it were released at once.
- Super armor absorbs melee hits, projectiles, and item hits. Grabs and command
  grabs still beat it.
- When both apply, the shorter of the auto-cancel landing and the L-cancel wins.

In the F9 overlay the hurtbox turns blue while intangible and purple during
super armor.

`npm run fighter:build` validates every override and reports the exact field
that is wrong; the full contract is in [fighter.schema.json](fighter.schema.json).
With `npm run dev` running, just save `fighter.json`: the page reloads with the
new frame data, or shows the validation error.
Turn on the in-match hitbox overlay (see "Debugging moves" below) while tuning.

## Syncing animation to hitboxes

An attack's clip is normally stretched evenly over the whole move
(startup + active + recovery), so the strike pose rarely lines up with the
first frame its hitbox is out. Pin it with `visual.keyFrames`: for each attack
slot, the 0-based atlas frame that should be on screen on the move's first
active frame.

```json
"visual": {
  "keyFrames": { "jab": 1, "forward_smash": 4, "neutral_air": 1 }
}
```

Frames before the key frame play over the wind-up, the key frame lands exactly
on the first frame a hitbox is out (the first active frame, or later when every
authored hitbox has an `activeStart`), and the rest play over the remaining
frames. Keys are the 17 attack slots (`jab` … `down_special`, snake_case).
`npm run fighter:check` rejects a key frame past the end of its atlas.
Fighters without key frames keep the even stretch.

## Alternate skins (palette swaps)

Skin `00` is the pack's own art. Up to three more skins are declared in
`visual.skins` and recoloured in the browser from the `00` atlases and
portrait, so they cost no extra files or downloads:

```json
"skins": [
  { "name": "Cobalt", "swaps": [
    { "from": "#cea521", "to": "#2a5cdc", "tolerance": 30 },
    { "from": "#d14637", "to": "#f0b428", "tolerance": 20 }
  ] },
  { "name": "Mint", "swaps": [{ "from": "#cea521", "to": "#23c48a" }] }
]
```

- Each swap moves one colour family: pixels whose hue is within `tolerance`
  degrees (default 24) of `from` take the hue of `to`, and keep their own
  shading relative to `from` (a shadow stays a shadow). The swap fades out
  toward the edge of the tolerance, so gradients do not band.
- Greys, whites, near-blacks, and transparent pixels never change, so
  outlines, metal, and eyes stay as drawn. A `from` colour that is too grey
  or dark to match anything is rejected by `fighter:build`.
- When two players pick the same fighter, the one who picked second moves
  to a different skin automatically.

Let the tool start you off. It reads the built atlases, lists the fighter's
colour families (flagging likely skin tones so faces are not recoloured),
and proposes three skins:

```sh
npm run fighter:skins -- my-fighter            # colour families + suggestion
npm run fighter:skins -- my-fighter --preview  # .generated/skins/my-fighter.png
npm run fighter:skins -- my-fighter --write    # store it in fighter.json (--replace to overwrite)
```

Then tune names, colours, and tolerances by hand. With `npm run dev`
running, open **Lab**, pick the fighter and a skin, and every save of
`fighter.json` reloads the preview. A fighter drawn only in greys and blacks
cannot be told apart by palette swaps; the tool says so, and such a pack
should leave `visual.skins` out.

## Sounds and voice

A pack may ship its own sounds in an `audio/` folder and list them per cue
in `fighter.json`. Every cue is optional; a cue left out uses the shared
sound (or none), so a pack can start with just a hurt voice:

```json
"audio": {
  "attribution": "Voice by Jo Example; swings recorded by the author",
  "license": { "id": "CC-BY-4.0", "url": "https://creativecommons.org/licenses/by/4.0/" },
  "cues": {
    "attack": ["audio/swing-1.ogg", "audio/swing-2.ogg", "audio/swing-3.ogg"],
    "smash": ["audio/heave.ogg"],
    "hurt": ["audio/oof-1.ogg", "audio/oof-2.ogg"],
    "ko": ["audio/scream.ogg"],
    "announce": ["audio/name.ogg"]
  }
}
```

| Cue | Plays when | Without it |
| --- | --- | --- |
| `attack` | the fighter starts a jab, tilt, aerial, or dash attack | shared swing |
| `smash` | the fighter starts a smash attack | the fighter's `attack` |
| `special` | the fighter starts a special move | the fighter's `attack` |
| `jump` | the fighter jumps | shared jump |
| `hurt` | the fighter takes a hit of 5% or more (not on super armor) | silent |
| `ko` | the fighter is KO'd off a blast line | silent (the shared KO blast still plays) |
| `taunt` | the fighter taunts | the fighter's `attack` |
| `victory` | the fighter wins | shared fanfare |
| `announce` | the fighter is picked on the character select screen | shared "ready" |

- List 1–4 files per cue; one plays at random each time, never the same one
  twice in a row, so three short swings sound far less robotic than one.
  A file may serve several cues.
- Formats: `.ogg` (the game's own sounds use it), `.mp3`, `.m4a`, or `.wav`.
  `.m4a` or `.mp3` is the safe choice if you care about older Safari.
- Budgets: 256 KiB per file and 2 MiB per pack. Keep cues short
  (attacks under 0.3 s, KO and victory under 1.5 s) and trim silence at the
  start, or the sound lands late.
- Level your files to a similar loudness (about −19 dBFS RMS matches the
  starter sounds); the game does not normalise them.
- `fighter:build` checks every path stays inside the pack, the extension,
  that the file really is that format (its first bytes), and the budgets.
  The files are bundled with the game, so they ship with the build.
- `attribution` and `license` are required: say who made the sounds and
  under which licence, exactly as for the art. Never use a real person's
  voice, or clips from games, shows, or films, without a licence that allows
  redistribution.

With `npm run dev` running, saving `fighter.json` or a sound reloads the
game. [`buckle`](buckle/) has a full set, synthesized by
`scripts/starter_fighter/generate_audio.py`.

## Debugging moves

For frame-by-frame work, open **Lab** from the main menu, pick a fighter and an
attack animation (for example `forward_smash`), and tick **Hitboxes & frame
data**. For attack slots the scrubber and ◀| |▶ step engine move frames instead
of sprite frames, and each frame shows:

- the sprite frame the game would display (with key frames applied);
- the engine's own active hitboxes, aligned like in a match (tick **Hurtbox**
  too for the hurtbox: blue while intangible, purple during super armor);
- the phase (startup / active / recovery), the strike frame, and the key frame.

During any match, press **F9** to toggle the collision overlay: yellow
capsules are hurtboxes (blue while intangible, purple during super armor), the
white square marks the
fighter origin, and active hitboxes are drawn as red (sweet), orange (normal),
or yellow (sour) circles. Adding `?hitboxes=1` to the URL starts with the
overlay on, and `?match=<p1-id>,<p2-id>` jumps straight into a match:

```text
http://localhost:4173/?match=my-fighter,rgs-stick&hitboxes=1&items=0
```

## Troubleshooting

- `Fighter pack ... already exists`: choose a new `id` or complete the existing
  pack.
- `... invalid status`: keep `draft` while working, then use `ready` only when
  the pack is complete.
- `slot ... missing` or fewer than `50/50 slots`: complete the classification in
  `render.json` without duplicating a role.
- `Generated output is stale`: run `npm run fighter:build`.
- Provenance or SHA-256 failure: fix the sources and their manifests, then run
  the pipeline again; do not bypass the validator.

For exhaustive validation of all 50 atlases for every fighter:

```sh
npm run fighter:check -- --deep
```
